# 검색 실험 계획 (Retrieval Experiment Plan)

> 작성 2026-09-05 · 개정 2026-09-06 · 이 문서는 **실행 전에 규칙을 먼저 고정하려고** 쓴다.
> 수치를 낸 뒤에 기준을 바꾸면 비교가 성립하지 않는다.
> 이 문서를 쓰는 시점에 측정은 하나도 하지 않았다.

## 0. 범위

**이번 실험이 다루는 것** — 검색 품질뿐이다.
질문을 넣으면 어떤 근거 chunk가 나오는지, 검색기를 바꾸면 그것이 어떻게 달라지는지.

**다루지 않는 것**

- LLM 답변 생성 — 생성기가 없으므로 faithfulness·answer_relevancy 같은 생성 지표는 계산할 수 없다.
  RAGAS는 이 실험의 지표가 아니다.
- 화면(UI) — 결과는 JSON과 표로 남긴다.
- 서비스 동작 변경 — 이번 파일럿에서 **서비스 API에 기권 임계값을 넣지 않는다.**
  임계값은 평가 스크립트 안에서만 분석한다.

이 실험은 **재현(reproduction)이 아니라 신규 측정**이다. 다른 문서·다른 질문·다른 지표이므로,
부트캠프 팀 프로젝트에서 나온 수치와 같은 표에 두거나 "재현했다"고 쓰지 않는다.

## 1. 용어를 먼저 정확히

현재 이 저장소의 `KeywordRetriever`는 **BM25가 아니다.** 토큰 겹침(term frequency)에
문서 빈도 역가중을 곱한 방식이고, BM25의 길이 정규화(b)나 포화 항(k1)이 없다.

문서·코드·결과표 어디서도 이것을 BM25라고 부르지 않는다.
`Hybrid`라는 말도 **실제 BM25를 구현한 뒤부터** 쓴다.

### 1.1 토큰화 — 지금 무엇을 하고 있는가

현재 토큰화는 정규식 `[0-9A-Za-z가-힣]+`로 문자열을 자른다. 실질적으로 **공백과 구두점을
경계로 어절을 끊는 방식**이고, 형태소 분석이나 조사 분리를 하지 않는다.
문자 단위로 자르는 것이 아니다.

그래서 `예산` · `예산은` · `예산의` · `예산을`이 서로 다른 토큰이 된다.

**여기서 단정하지 않는 것**

- "어휘 기반 검색의 점수가 반드시 낮게 나온다"고 단정하지 않는다.
  질문과 문서가 같은 표현을 쓰면 어절 단위로도 그대로 맞는다.
- "Dense가 반드시 유리하다"고 단정하지 않는다.
  Dense도 임베딩 모델이 쓰는 토크나이저의 영향을 받고, 한국어 처리 품질은 모델마다 다르다.

**말할 수 있는 것은 여기까지다** — 형태소·조사를 분리하지 않는 토큰화는 어휘 기반 검색에
**불리하게 작용할 수 있다.** 얼마나 불리한지는 재 봐야 안다. 그래서 토큰화를 검색 방식과
섞지 않고 **별도 축으로 분리해서** 측정한다(§2의 R1a / R1b).

## 2. 실험 대상 — 검색기 사다리

한 번에 하나씩 올린다. 각 단계는 직전 단계와만 비교한다.

| # | 이름 | 내용 | 비교 대상 |
|---|---|---|---|
| R0 | `keyword` | 현재 구현 (토큰 겹침 + 문서 빈도 역가중, 어절 토큰화) | 기준선 |
| R1a | `bm25-simple` | 실제 BM25 (k1·b 명시) + **현재의 단순 토큰화** | R0 |
| R1b | `bm25-ko` | 실제 BM25 + **한국어 형태소 토큰화** | R1a — 토큰화 축만 다름 |
| R2 | `dense` | 로컬 임베딩 모델 | R0 · R1a · R1b |
| R3 | `hybrid-rrf` | BM25 + Dense 를 RRF로 결합 | 결합에 쓴 두 검색기 |
| R4 | `hybrid-rrf-rerank` | R3 + Reranker (실패 시 R3 결과 유지) | R3 |

R1a와 R1b는 **검색 알고리즘이 같고 토큰화만 다르다.** 이 한 쌍이 있어야
"BM25 대 Dense"의 차이에서 토큰화 몫을 떼어낼 수 있다.
R3의 BM25 쪽에 R1a를 쓸지 R1b를 쓸지는 R1a·R1b 결과를 보고 정하고, 어느 쪽을 썼는지 명시한다.

**제약** — Dense와 Reranker의 모델은 로컬에서 도는 것을 쓴다. API 키를 요구하는 임베딩은
쓰지 않는다. 키·네트워크 없이 `pytest -q`가 도는 성질을 유지하기 위해서다.
모델 다운로드가 필요한 테스트는 opt-in 마커로 분리하고 기본 CI에서는 제외한다.

### 2.1 R1b 형태소 토큰화 — 후보와 선택 기준 (아직 확정하지 않음)

| 후보 | 방식 | 확인할 점 |
|---|---|---|
| `kiwipiepy` (Kiwi) | C++ 구현 + 파이썬 바인딩 | 휠 설치만으로 되는지, 모델 데이터가 휠에 포함되는지, 라이선스 |
| `mecab-ko` + `mecab-ko-dic` | 시스템 패키지 + 사전 | 사전 설치가 CI에서 필요한지, 설치 절차의 재현성 |
| KoNLPy (Okt · Komoran 등) | JVM 기반 | Java 런타임이 필요한지, CI 이미지에 부담이 되는지 |
| `soynlp` | 비지도 통계 | 형태소 분석기가 아니라 분리 품질이 문서 집합에 좌우됨 |

**선택 기준** (전부 만족하지 않아도 되지만, 어긋나는 항목은 결과에 적는다)

1. `pip install`만으로 설치되는가 — 시스템 패키지·JVM이 필요하면 CI 재현성이 떨어진다
2. 첫 실행에 네트워크(사전·모델 다운로드)가 필요한가
3. 버전을 고정할 수 있는가, 같은 입력에 같은 출력이 나오는가
4. 라이선스가 공개 저장소에 담기에 문제없는가
5. 조사·어미 분리가 실제 RFP 문장에서 쓸 만한가 — 샘플 몇 문장으로 눈으로 확인

선정하면 라이브러리 이름·버전·설정을 `config.yaml`과 결과표에 함께 적는다.

## 3. 코퍼스와 청킹 — 고정이 아니라 버전 관리

청킹 규칙을 "절대 바꾸지 않는다"고 두면 **청크 크기·오버랩 자체를 실험할 수 없다.**
바꿔도 되게 하되, 바꾸면 새 실험 ID가 되도록 한다.

```yaml
corpus_version: rfp-demo-v1        # 문서 집합이 바뀌면 올린다
chunker_version: fixed-500-overlap-80-v1
config_hash: <청킹 파라미터의 sha256 앞 8자리>
experiment_id: <corpus_version>__<chunker_version>__<retriever>
```

- 문서 원본은 저장소에 두지 않는다. 해시로 대조만 가능하게 한다.
- 청킹 파라미터를 바꾸면 `chunker_version`을 올리고 **기존 결과는 폐기하지 않는다.**
  다른 `experiment_id`의 결과로 남긴다.
- `experiment_id`가 다른 결과끼리는 같은 표에 넣지 않는다.

### 3.1 추출 텍스트가 좌표의 기준이다

정답 좌표와 chunk 좌표는 **원본 파일이 아니라 정규화된 추출 텍스트**를 기준으로 한다.
추출기나 정규화 규칙이 바뀌면 좌표가 통째로 어긋나므로, 버전과 해시를 함께 남긴다.

문서마다 기록할 최소 메타데이터:

```yaml
document_id: doc-001
document_sha256: <원본 파일 해시>
extracted_text_sha256: <정규화된 추출 텍스트 해시>
extractor_version: <추출기 이름·버전>
normalization_version: <공백·줄바꿈·유니코드 정규화 규칙 버전>
```

`extractor_version` 또는 `normalization_version`이 바뀌면 `corpus_version`을 올린다.

각 chunk도 자기가 어느 원문 범위를 담고 있는지, 어느 추출 텍스트 기준인지 함께 저장한다.

```json
{
  "chunk_id": "rfp-demo-v1/doc-001#0007",
  "document_id": "doc-001",
  "extracted_text_sha256": "…",
  "page": 12,
  "section": "3.2 예산",
  "char_start": 8412,
  "char_end": 8907
}
```

## 4. 평가셋 — 정답은 chunk가 아니라 원문 위치에 건다

**chunk ID로 정답을 라벨링하지 않는다.** 청킹이 바뀌면 라벨이 통째로 무효가 되기 때문이다.
정답은 추출 텍스트의 문자 좌표에 건다.

```yaml
- qid: q014
  question: "이 사업의 총 예산은 얼마인가?"
  type: single          # single | followup | filter | unanswerable
  evidence:
    - document_id: doc-001
      document_sha256: "…"
      extracted_text_sha256: "…"
      extractor_version: "…"
      normalization_version: "…"
      page: 12
      section: "3.2 예산"
      char_start: 8450
      char_end: 8612
      relevance_grade: 2   # 2=직접 답, 1=부분 근거, 0=무관
```

### 4.1 겹침 판정 — 느슨한 기준과 엄격한 기준을 따로 보고한다

검색된 chunk의 `[char_start, char_end)` 와 정답 `[char_start, char_end)` 의 겹침으로 판정한다.
**두 기준을 각각 계산하고, 합치거나 평균 내지 않는다.**

| 기준 | 정의 | 성격 |
|---|---|---|
| `overlap_any` | 1자라도 겹치면 적중 | 느슨 |
| `overlap_ratio ≥ 0.5` | 정답 구간의 절반 이상을 덮으면 적중 | 엄격 |

`overlap_ratio`의 **분모는 정답 evidence 구간의 길이**다 —
`|겹침| / (evidence.char_end - evidence.char_start)` 이고 IoU가 아니다.
큰 chunk가 작은 정답 구간을 통째로 덮으면 값이 1.0이 된다. 그래서 두 기준을 함께 보고,
결과표에 **평균 chunk 길이**와 **평균 검색 컨텍스트 길이**(상위 k개 chunk 길이의 합)를
반드시 함께 적는다. 청크를 키워서 적중률을 올린 것인지 구분할 수 있어야 한다.

### 4.2 이진 판정 기준

`relevance_grade ≥ 1` 을 적중으로 본다.
`Recall@k` · `Precision@k` · `Hit@k` · `MRR` 은 이 기준을 쓰고,
`nDCG@k` 만 등급(2 / 1 / 0)을 이득으로 그대로 쓴다.
이 문장이 없으면 같은 `metrics.json`에서 서로 다른 수치가 나온다.

### 4.3 평가셋 동결과 수정

질문도 라벨도 같은 사람이 만들고, 그다음에 검색 결과를 본다.
결과를 본 뒤 라벨을 손대면 수치가 오염되므로 순서를 규칙으로 고정한다.

1. 질문과 정답 라벨을 **원문만 보고** 작성한다. 이 단계에서 검색기를 돌리지 않는다
2. 평가셋을 커밋한다 — 이 커밋이 **동결 시점**이다
3. 그 뒤에 첫 측정을 실행한다
4. 결과에는 **평가셋 커밋 해시와 측정 커밋 해시를 함께 적는다.**
   두 해시의 순서로 "라벨이 결과보다 먼저였다"가 검증 가능해진다

**오류를 발견해도 기존 버전을 덮어쓰지 않는다.**

- `evalset_version`을 올린다 (`rfp-demo-eval-v1` → `v2`)
- `docs/EVALSET_CHANGELOG.md`에 **무엇을 왜 고쳤는지** 적는다
- 새 버전으로 필요한 실험을 다시 측정한다
- **다른 `evalset_version`의 결과를 같은 열에서 비교하지 않는다.**
  옛 버전 결과도 지우지 않고 남긴다

### 4.4 규모

질문 20~30개. 유형 배분을 먼저 정하고 라벨링한다.
이 규모는 **파일럿 평가셋**이다 — §5.4의 해석 규칙을 반드시 함께 적용한다.

## 5. 지표

### 5.1 답변 가능한 질문 (single · followup · filter)

`k ∈ {1, 3, 5, 10}` 에서 전부 계산한다. 겹침 기준 두 가지 각각에 대해 계산한다.

- `Recall@k` — 정답 evidence 중 덮인 비율
- `Precision@k` — 반환한 chunk 중 정답과 겹치는 비율
- `Hit@k` — 상위 k에 정답이 하나라도 있으면 1
- `MRR` — 첫 정답의 역순위
- `nDCG@k` — `relevance_grade`를 이득으로 사용

### 5.2 답변불가 질문 — 평균에 섞지 않는다

정답이 빈 집합이라 Recall이 정의되지 않는다. 별도로 본다.

**이번 파일럿에서 보고하는 것은 검색기별 threshold sweep뿐이다.**

- `false_evidence_rate@θ` — 근거가 없는 질문인데 θ 이상의 근거를 반환한 비율
- `miss_rate@θ` — 근거가 있는 질문인데 θ 때문에 아무것도 반환하지 못한 비율

두 값을 **θ를 훑은 곡선으로** 남긴다. 하나의 표에 두 지표를 함께 그려야 맞교환이 보인다.

**하지 않는 것**

- 같은 평가셋에서 가장 좋은 θ 하나를 고른 뒤, 그 θ의 성능을 결과로 보고하지 않는다.
  같은 데이터에서 고르고 같은 데이터에서 평가하면 낙관적으로 치우친다.
- 운영에 쓸 θ가 필요해지면 **calibration set에서 정하고 test set에서 평가한다.**
  파일럿 규모에서 그렇게 나누면 양쪽 다 너무 작아지므로, 이번에는 나누지 않고 곡선만 보고한다.
- **순위만으로는 기권을 결정할 수 없다.** 순위는 항상 1위를 만들어 내기 때문에,
  "근거가 없다"는 판단에는 점수나 별도의 판정 기준이 필요하다. 이 사실을 결과에 적는다.

θ는 **검색기마다 따로 잡는다.** 점수 스케일이 다르기 때문이다 —
R0·R1은 TF·IDF 규모이고 RRF 점수는 `1/(k+rank)` 규모라 자릿수가 다르다.
하나의 θ로 여러 검색기를 비교하면 임계값이 아니라 스케일을 비교하게 된다.

서비스 API에는 이번에 임계값을 넣지 않는다. 평가 스크립트가 검색기를 직접 호출해
충분히 큰 k의 점수 목록을 받은 뒤, 그 위에서 θ를 훑는다.
`/retrieve` · `/ask` 의 응답 계약과 기존 테스트는 건드리지 않는다.

### 5.3 보고 규칙

- **평균만 보고하지 않는다.** 문항별 결과를 `metrics.json`에 전부 남긴다.
- **실패한 질문을 공개한다.** 어떤 유형에서 왜 틀렸는지 함께 적는다.
- 검색기가 기준선을 이기지 못해도 그대로 싣는다. **Dense나 Hybrid가 더 낮게 나와도 공개한다.**
- 결과표마다 다음을 함께 적는다 —
  `experiment_id` · 토큰화 방식 · 겹침 기준 · 평균 chunk 길이 · 평균 검색 컨텍스트 길이 ·
  `evalset_version` · 평가셋 커밋 해시 · 측정 커밋 해시

### 5.4 통계 해석 — 파일럿 규모의 한계

20~30문항은 **파일럿 평가셋**이다. 다음을 지킨다.

- 평균값 차이만으로 **일반적인 우위를 주장하지 않는다.** "이 평가셋에서는" 을 붙인다
- 검색기 쌍마다 **문항별 paired difference를 공개한다** — 어떤 질문에서 이기고 졌는지
- 가능하면 **paired bootstrap으로 불확실성 구간**을 함께 낸다
- 구간이 겹치면 우열을 주장하지 않는다. "차이를 확인하지 못했다"로 적는다
- 표본이 작다는 한계를 결과 문서 첫머리에 적는다

## 6. 산출물 위치

측정을 시작할 때 만든다. **이번 문서화 단계에서는 만들지 않는다.**

```
evidence/<experiment_id>/
├── README.md         무엇을·왜·무엇을 확인했나 + 표본 한계
├── config.yaml       corpus/chunker/retriever/tokenizer 설정 + config_hash
├── environment.txt   python·라이브러리 버전, OS
├── inputs.sha256     원본 문서 해시 + 추출 텍스트 해시
├── metrics.json      집계 + 문항별 결과 + paired difference
├── failures.md       틀린 질문과 원인
└── commands.txt      실행한 명령 그대로
```

## 7. 순서

1. 공개 가능한 RFP 문서 선정
2. 추출·정규화 규칙 확정 · `document_sha256` / `extracted_text_sha256` / 버전 기록
3. 청킹 구현 (`char_start`/`char_end` 포함) · `chunker_version` 부여
4. 질문 20~30개 작성 · 원문 evidence 좌표로 라벨링 — **검색기를 돌리지 않는다**
5. **평가셋 커밋·동결** (§4.3)
6. 평가 스크립트 구현 (§5 지표 전부 · θ sweep 포함)
7. **R0 `keyword` 기준선 측정**
8. R1a `bm25-simple` 구현·측정
9. R1b `bm25-ko` 구현·측정
10. R2 `dense` 구현·측정
11. R3 `hybrid-rrf` 구현·측정
12. R4 Reranker 구현·측정 (실패 시 R3 결과 유지)
13. 문항별 실패 분석 · 답변불가 threshold sweep 분석

## 8. 중단·보류 기준

- 라벨링에서 정답 구간이 모호한 질문은 평가셋에서 **뺀다.** 억지로 라벨링하지 않는다.
- R1b 후보 중 §2.1 기준을 만족하는 것이 없으면 **R1b를 건너뛴다.**
  건너뛰면 "토큰화 축을 통제하지 못했다"를 결과에 명시하고, R1a와 R2의 비교에 각주를 단다.
- 로컬 Dense 모델이 CI 제약(키·네트워크 없음)을 깨면 opt-in으로 분리하고, 그 사실을 결과에 적는다.
- 어느 단계에서 멈추더라도 그 시점까지의 결과는 `evidence/`에 남기고 공개한다.
