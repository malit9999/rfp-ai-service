# 검색 실험 계획 (Retrieval Experiment Plan)

> 작성 2026-09-05 · 개정 2026-09-06 · 이 문서는 **실행 전에 규칙을 먼저 고정하려고** 쓴다.
> 수치를 낸 뒤에 기준을 바꾸면 비교가 성립하지 않는다.
> 이 문서를 쓰는 시점에 측정은 하나도 하지 않았다.

## 0. 범위

**이번 실험이 다루는 것** — 검색 품질뿐이다.
질문을 넣으면 어떤 근거 chunk가 나오는지, 검색기를 바꾸면 그것이 어떻게 달라지는지.

**다루지 않는 것**

- LLM 답변 생성 — 생성기가 없으므로 faithfulness·answer_relevancy 같은 생성 지표는 계산할 수 없다.
  RAGAS는 이 실험의 지표가 아니다.
- 화면(UI) — 결과는 JSON과 표로 남긴다.
- 서비스 동작 변경 — 이번 파일럿에서 **서비스 API에 기권 임계값을 넣지 않는다.**
  임계값은 평가 스크립트 안에서만 분석한다.

이 실험은 **재현(reproduction)이 아니라 신규 측정**이다. 다른 문서·다른 질문·다른 지표이므로,
부트캠프 팀 프로젝트에서 나온 수치와 같은 표에 두거나 "재현했다"고 쓰지 않는다.

## 1. 용어를 먼저 정확히

현재 이 저장소의 `KeywordRetriever`는 **BM25가 아니다.** 토큰 겹침(term frequency)에
문서 빈도 역가중을 곱한 방식이고, BM25의 길이 정규화(b)나 포화 항(k1)이 없다.

문서·코드·결과표 어디서도 이것을 BM25라고 부르지 않는다.
`Hybrid`라는 말도 **실제 BM25를 구현한 뒤부터** 쓴다.

### 1.1 토큰화 — 지금 무엇을 하고 있는가

현재 토큰화는 정규식 `[0-9A-Za-z가-힣]+`로 문자열을 자른다. 실질적으로 **공백과 구두점을
경계로 어절을 끊는 방식**이고, 형태소 분석이나 조사 분리를 하지 않는다.
문자 단위로 자르는 것이 아니다.

그래서 `예산` · `예산은` · `예산의` · `예산을`이 서로 다른 토큰이 된다.

**여기서 단정하지 않는 것**

- "어휘 기반 검색의 점수가 반드시 낮게 나온다"고 단정하지 않는다.
  질문과 문서가 같은 표현을 쓰면 어절 단위로도 그대로 맞는다.
- "Dense가 반드시 유리하다"고 단정하지 않는다.
  Dense도 임베딩 모델이 쓰는 토크나이저의 영향을 받고, 한국어 처리 품질은 모델마다 다르다.

**말할 수 있는 것은 여기까지다** — 형태소·조사를 분리하지 않는 토큰화는 어휘 기반 검색에
**불리하게 작용할 수 있다.** 얼마나 불리한지는 재 봐야 안다. 그래서 토큰화를 검색 방식과
섞지 않고 **별도 축으로 분리해서** 측정한다(§2의 R1a / R1b).

## 2. 실험 대상 — 검색기 사다리

한 번에 하나씩 올린다. 각 단계는 직전 단계와만 비교한다.

| # | 이름 | 내용 | 비교 대상 |
|---|---|---|---|
| R0 | `keyword` | 현재 구현 (토큰 겹침 + 문서 빈도 역가중, 어절 토큰화) | 기준선 |
| R1a | `bm25-simple` | 실제 BM25 (k1·b 명시) + **현재의 단순 토큰화** | R0 |
| R1b | `bm25-ko` | 실제 BM25 + **한국어 형태소 토큰화** | R1a — 토큰화 축만 다름 |
| R1c | `bm25-ko-dict` | R1b + 사용자 사전 (도메인 용어) | R1b — **사전 축만 다름 · 후순위** |
| R2 | `dense` | 로컬 임베딩 모델 | R0 · R1a · R1b |
| R3 | `hybrid-rrf` | BM25 + Dense 를 RRF로 결합 | 결합에 쓴 두 검색기 |
| R4 | `hybrid-rrf-rerank` | R3 + Reranker (실패 시 R3 결과 유지) | R3 |

R1a와 R1b는 **검색 알고리즘이 같고 토큰화만 다르다.** 이 한 쌍이 있어야
"BM25 대 Dense"의 차이에서 토큰화 몫을 떼어낼 수 있다.

**R1c는 R0~R4 사다리에 넣지 않는다.** 사용자 사전은 R1b 결과를 본 뒤에 별도로 붙이고,
기존 결과를 덮지 않고 새 `experiment_id`로 남긴다. 사전을 처음부터 넣으면 형태소 분석의
효과와 사전의 효과가 섞인다.
R3의 BM25 쪽에 R1a를 쓸지 R1b를 쓸지는 R1a·R1b 결과를 보고 정하고, 어느 쪽을 썼는지 명시한다.

**제약** — Dense와 Reranker의 모델은 로컬에서 도는 것을 쓴다. API 키를 요구하는 임베딩은
쓰지 않는다. 키·네트워크 없이 `pytest -q`가 도는 성질을 유지하기 위해서다.
모델 다운로드가 필요한 테스트는 opt-in 마커로 분리하고 기본 CI에서는 제외한다.

### 2.1 R1b 형태소 토큰화 — `kiwipiepy` 우선 검증 결과

후보 중 `kiwipiepy`를 먼저 검증했다. **2026-09-06 · Python 3.12.13 클린 가상환경.**

| 항목 | 결과 |
|---|---|
| 설치 | `pip install kiwipiepy` 만으로 완료 (약 8초). JVM·시스템 패키지 불필요 |
| 버전 | `kiwipiepy==0.23.2` · `kiwipiepy_model==0.23.0` (모델이 별도 패키지로 자동 설치) |
| 전이 의존성 | `numpy` · `tqdm` 둘뿐 |
| 모델 배포 방식 | **휠에 포함.** `site-packages/kiwipiepy_model/` 104MB (`default.dict`, `sj.morph`, `*.mdl` 등) |
| 첫 실행 네트워크 | **불필요.** 프록시를 죽은 포트로 돌려 네트워크를 막고 실행해도 정상 동작 |
| 결정성 | 같은 입력을 별도 프로세스에서 두 번 실행 → 토큰 시퀀스 해시 동일 (`0fdf5963666c68b7`) |
| 라이선스 | **표기가 엇갈린다** — 아래 별도 항목 참조 |

실제 RFP 문장으로 확인한 분해 결과:

```
입력  : 본 사업의 예산 총액은 3억원이며, 부가가치세를 포함한 금액이다. 예산은 분할 집행한다.
출력  : 본/MM 사업/NNG 의/JKG 예산/NNG 총액/NNG 은/JX 3/SN 억/NR 원/NNB …
        예산/NNG 은/JX 분할/NNG 집행/NNG 하/XSV ᆫ다/EF
```

`예산은` → `예산` + `은/JX` 로 조사가 떨어진다. R1b가 노리는 지점이 이것이다.
같은 문장에서 `부가가치세` 가 `부가/NNG` + `가치세/NNG` 로 쪼개지는 것도 확인했다 —
도메인 용어가 분해될 수 있다는 뜻이므로, 사용자 사전 사용 여부는 실제 문서를 보고 정한다.

#### 라이선스 표기가 엇갈린다

한 줄로 "LGPL v3"라고 적지 않는다. 설치본에서 확인한 두 값이 다르다.

| 출처 | 내용 |
|---|---|
| `kiwipiepy-0.23.2.dist-info/LICENSE.txt` (공식 라이선스 본문) | "GNU Lesser General Public License … **either version 2.1 of the License, or (at your option) any later version**" — 즉 **LGPL 2.1 이상** |
| 패키지 메타데이터 (`METADATA`) | `License: LGPL v3 License` · `Classifier: … GNU Lesser General Public License v3 (LGPLv3)` |
| `kiwipiepy_model-0.23.0.dist-info` | 라이선스 **본문 파일이 없고** 메타데이터에만 LGPLv3 표기 |

**법적 적합성을 여기서 단정하지 않는다.** 지금은 라이브러리를 수정하지 않고 그대로
import 해서 평가 스크립트에서만 쓰는 사용이고, 배포물에 포함시키지 않는다.
**배포 형태가 바뀌면**(바이너리 동봉, 서비스 이미지에 포함, 수정 후 재배포 등)
**다시 확인한다.**

#### 채택과 고정

`kiwipiepy==0.23.2` · `kiwipiepy_model==0.23.0` 을 R1b에 채택한다.
버전은 `requirements-eval.txt`에 `==`로 고정하고, **서비스 `requirements.txt`에는 넣지 않는다**
(런타임 의존성이 아니라 평가 전용이다).

### 2.2 R1b 토큰 정책 `tok-ko-v1`

질의와 문서에 **같은 토크나이저와 같은 정책**을 적용한다. 한쪽만 바꾸면 비교가 깨진다.

#### 포함 품사

| 태그 | 무엇 | 왜 넣는가 |
|---|---|---|
| `NNG` · `NNP` | 일반·고유명사 | 내용어의 중심 |
| `NNB` | 의존명사 | `원` · `점` · `건` — 금액·배점 질의의 핵심 단위 |
| `NR` · `SN` | 수사·숫자 | 예산·배점 값 |
| `SL` | 외국어 | `RAG` · `AI` 같은 영문 용어 |
| `SH` | 한자 | 법령·기관명에 섞여 나온다 |
| `XR` | 어근 | 명사성 어근 |
| `VV` · `VA` | 동사·형용사 어간 | `제출` 같은 명사형이 없을 때의 단서 |
| `W_SERIAL` | 날짜·시각·일련 | `2026/09/23` · `10:00` — 일정 질의의 핵심 |

#### 제외 품사

조사(`J*`) · 어미(`E*`) · 접사(`XS*` · `XP*`) · 관형사(`MM`) · 부사(`MA*`) ·
감탄사(`IC`) · 대명사(`NP`) · 보조용언(`VX`) · 지정사(`VCP` · `VCN`) ·
구두점과 기호(`SF` · `SP` · `SS*` · `SE` · `SO` · `SW`).

대명사를 빼는 이유는 후속 질문의 지시어(`그 사업`)가 색인 신호가 되지 못하기 때문이다.

#### 원형화

**하지 않는다.** Kiwi가 돌려주는 형태소 표층형(`token.form`)을 그대로 쓰고,
소문자화만 적용한다. 용언은 이미 어간까지 잘려 나오므로(`집행/NNG` + `하/XSV`)
동사 원형(`집행하다`)을 복원하지 않는다. 복원 규칙을 넣으면 그 규칙 자체가
또 하나의 실험 변수가 된다.

#### 숫자·영문·복합명사

실제 문장으로 확인한 동작(2026-09-06)을 기준으로 정한다.

| 입력 | Kiwi 출력 | 정책 |
|---|---|---|
| `1,199,886,020원` | `1,199,886,020/SN` + `원/NNB` | **쉼표를 제거하지 않는다.** 질의도 같은 토크나이저를 지나므로 표기가 대칭이다 |
| `2026/09/23`, `10:00` | `W_SERIAL` | 한 토큰으로 유지 |
| `RAG`, `AI` | `SL` | 소문자화해서 색인 |
| `부가가치세` | `부가/NNG` + `가치세/NNG` | **분해형만 색인한다.** 원 어절을 따로 추가하지 않는다 |
| `하도급지킴이` | `하도급/NNG` + `지킴이/NNG` | 같음 |
| `차등점수제` | `차등/NNG` + `점수/NNG` + `제/XSN` | `제/XSN`은 제외 품사라 버려진다 |

**알려진 한계** — 금액을 쉼표 없이 쓴 질의(`1199886020`)는 매칭되지 않는다.
이 한계를 결과에 적고, 필요해지면 숫자 정규화를 **별도 실험**으로 분리한다.

#### 사용자 사전

**초기 R1b에는 사용자 사전을 넣지 않는다.** `부가가치세`처럼 도메인 용어가 쪼개지는 것을
알고 있지만, 사전을 처음부터 넣으면 형태소 분석의 효과와 사전의 효과가 섞인다.

사전 실험은 **R1b 결과를 확인한 뒤 `R1c`로 분리**한다. R1c는 기존 결과를 덮지 않고
새 `experiment_id`로 남기며, 비교 대상은 R1b 하나다.

**다른 후보** (kiwipiepy로 진행하지 못할 때만 검토)

| 후보 | 확인할 점 |
|---|---|
| `mecab-ko` + `mecab-ko-dic` | 시스템 패키지·사전 설치가 CI에서 재현되는지 |
| KoNLPy (Okt·Komoran) | JVM 필요 — CI 이미지 부담 |
| `soynlp` | 형태소 분석기가 아니라 분리 품질이 문서 집합에 좌우됨 |

## 3. 코퍼스와 청킹 — 고정이 아니라 버전 관리

**파일럿 코퍼스는 문서 1건이다.** 대상 문서와 이용 조건, 취득 절차는
[`CORPUS_RFP_DEMO_V1.md`](CORPUS_RFP_DEMO_V1.md)에 따로 적었다.
추출·정규화 규칙과 재현 조건은 [`EXTRACTION_CONTRACT.md`](EXTRACTION_CONTRACT.md)에 있다.

청킹 규칙을 "절대 바꾸지 않는다"고 두면 **청크 크기·오버랩 자체를 실험할 수 없다.**
바꿔도 되게 하되, 바꾸면 새 실험 ID가 되도록 한다.

```yaml
corpus_version: rfp-demo-v1        # 문서 집합이 바뀌면 올린다
chunker_version: fixed-500-overlap-80-v1
config_hash: <청킹 파라미터의 sha256 앞 8자리>
experiment_id: <corpus_version>__<chunker_version>__<retriever>
```

- 문서 원본은 저장소에 두지 않는다. 해시로 대조만 가능하게 한다.
- 청킹 파라미터를 바꾸면 `chunker_version`을 올리고 **기존 결과는 폐기하지 않는다.**
  다른 `experiment_id`의 결과로 남긴다.
- `experiment_id`가 다른 결과끼리는 같은 표에 넣지 않는다.

**청킹 기준선은 `C0 = fixed-500-overlap-80-v1` 이다.**
R0~R4를 비교하는 동안 이 값을 **고정한다.** 검색기를 비교하는 실험에서 청킹이 같이 움직이면
어느 쪽이 차이를 만들었는지 알 수 없기 때문이다.
청크 크기·오버랩을 바꾸는 것은 **별도 실험**으로 분리하고, 그때 `chunker_version`을 올린다.

### 3.1 추출 텍스트가 좌표의 기준이다

정답 좌표와 chunk 좌표는 **원본 파일이 아니라 정규화된 추출 텍스트**를 기준으로 한다.
추출기나 정규화 규칙이 바뀌면 좌표가 통째로 어긋나므로, 버전과 해시를 함께 남긴다.

**형식이 안정성을 주지 않는다.** HWPX가 XML 기반이라는 사실만으로 좌표가 안정적이라고
말하지 않는다. 표를 펼치는 순서, 셀 구분자, 빈 문단 처리에 따라 결과 텍스트가 달라진다.
안정성은 [`EXTRACTION_CONTRACT.md`](EXTRACTION_CONTRACT.md)의 규칙을 고정해야 생긴다.

문서마다 기록할 최소 메타데이터:

```yaml
document_id: doc-001
document_sha256: <원본 파일 해시>
extracted_text_sha256: <정규화된 추출 텍스트 해시>
extractor_version: <추출기 이름·버전>
normalization_version: <공백·줄바꿈·유니코드 정규화 규칙 버전>
```

`extractor_version` 또는 `normalization_version`이 바뀌면 `corpus_version`을 올린다.

각 chunk도 자기가 어느 원문 범위를 담고 있는지, 어느 추출 텍스트 기준인지 함께 저장한다.

```json
{
  "chunk_id": "rfp-demo-v1/doc-001#0007",
  "document_id": "doc-001",
  "extracted_text_sha256": "…",
  "page": 12,
  "section": "3.2 예산",
  "char_start": 8412,
  "char_end": 8907
}
```

## 4. 평가셋 — 정답은 chunk가 아니라 원문 위치에 건다

**chunk ID로 정답을 라벨링하지 않는다.** 청킹이 바뀌면 라벨이 통째로 무효가 되기 때문이다.
정답은 추출 텍스트의 문자 좌표에 건다.

```yaml
- qid: q014
  question: "이 사업의 총 예산은 얼마인가?"
  type: single          # single | followup | filter | unanswerable
  evidence:
    - document_id: doc-001
      document_sha256: "…"
      extracted_text_sha256: "…"
      extractor_version: "…"
      normalization_version: "…"
      page: null            # HWPX 본문 XML에 쪽 경계가 없다 (추출 계약 §2.3)
      section: "3.2 예산"
      char_start: 8450
      char_end: 8612
      relevance_grade: 2    # 2=직접 답, 1=부분 근거. **0은 쓰지 않는다**
```

### 4.1 라벨 작성 규칙

**strict 지표에 맞추려고 ground truth 를 자르지 않는다.** 지표가 라벨을 왜곡하면
평가가 아니라 자기충족이 된다.

- evidence 길이를 **인위적으로 제한하지 않는다** (400자 같은 상한을 두지 않는다)
- 답을 뒷받침하는 **최소한의 완결된 의미 단위**로 라벨링한다
- **논리적으로 독립된 근거일 때만** 여러 span으로 나눈다. 길이를 줄이려고 쪼개지 않는다
- `relevance_grade` 는 **1 또는 2만** 쓴다. 무관하면 라벨하지 않는다(0을 쓰지 않는다)
- 결과에 **evidence 길이와 span 수를 함께 기록한다**

### 4.2 겹침 판정 — 느슨한 기준과 엄격한 기준을 따로 보고한다

| 기준 | 정의 | 성격 |
|---|---|---|
| `overlap_any` | 1자라도 겹치면 적중 | 느슨 |
| `overlap_ratio ≥ 0.5` | 정답 구간의 절반 이상을 덮으면 적중 | 엄격 |

두 기준을 각각 계산하고 **합치거나 평균 내지 않는다.**
`overlap_ratio` 의 분모는 **정답 evidence 구간의 길이**이고 IoU가 아니다.

겹침은 `document_id` 와 `extracted_text_sha256` 이 **모두 같을 때만** 인정한다.
같은 문서인데 해시가 다르면 좌표를 비교할 수 없으므로 **계산을 중단한다.**

### 4.3 chunk qrel 변환

순위 지표는 evidence 좌표를 **현재 chunker 의 chunk 단위 qrel 로 변환한 뒤** 계산한다.

```
R_any    = { c : ∃e, overlap(c,e) > 0 }
R_strict = { c : ∃e, overlap(c,e) / |e| ≥ 0.5 }
grade(c) = max{ e.relevance_grade : criterion(c,e) 통과 }   (없으면 0)
```

좌표 기준으로 직접 계산하면 **같은 evidence 를 덮는 chunk 가 여러 개일 때 nDCG 가 1을 넘는다.**
qrel 변환이 그것을 막는다. 대가로 **순위 지표는 chunker 에 묶인다** — 같은
`chunker_version` 안에서만 비교하고, chunker 가 다른 비교에는 `EvidenceCoverage@k` 를 쓴다.

### 4.4 strict 도달 가능성 (reachability)

`C0` 는 chunk 500자다. 따라서 evidence 가 1,000자를 넘으면 어떤 단일 chunk 도 절반을
덮을 수 없어 **strict 적중이 구조적으로 불가능**하다. 검색기 성능과 무관한 한계다.

라벨을 자르지 않기로 했으므로, 이 경우는 **task 수준에서 먼저 판정한다.**

- `strict_reachable = false`
- 해당 문항의 strict `Hit` · `Precision` · `MRR` · `nDCG` 는 **모두 `None`**
- strict macro 평균에서 **제외**
- `strict_reachable_count / answerable_count` 와 `strict_reachability_rate` 를 **반드시 함께 보고**
- 지표별로 예외 처리하지 않는다. `IDCG@k == 0` 도 따로 다루지 않고 이 판정이 먼저 걸린다

**`EvidenceCoverage@k` 는 모든 answerable 문항을 계속 포함한다.** 그래서 청킹 때문에
근거를 충분히 담지 못한 문제가 Coverage 에서 숨겨지지 않는다.

반대로 answerable 문항인데 **any qrel 까지 0개면 결과가 아니라 자료 오류**다.
`None` 으로 넘어가지 않고 좌표·`document_id`·`extracted_text_sha256`·chunk 커버리지 문제로
보고 **계산을 중단한다.**

### 4.5 평가셋 동결과 수정

질문도 라벨도 같은 사람이 만들고, 그다음에 검색 결과를 본다.
결과를 본 뒤 라벨을 손대면 수치가 오염되므로 순서를 규칙으로 고정한다.

1. 질문과 정답 라벨을 **원문만 보고** 작성한다. 이 단계에서 검색기를 돌리지 않는다
2. 평가셋을 커밋한다 — 이 커밋이 **동결 시점**이다
3. 그 뒤에 첫 측정을 실행한다
4. 결과에는 **평가셋 커밋 해시와 측정 커밋 해시를 함께 적는다**

**오류를 발견해도 기존 버전을 덮어쓰지 않는다.** `evalset_version` 을 올리고
`docs/EVALSET_CHANGELOG.md` 에 이유를 적은 뒤 필요한 실험을 다시 측정한다.
다른 `evalset_version` 의 결과를 같은 열에서 비교하지 않는다.

### 4.6 규모

질문 20~30개. 유형 배분을 먼저 정하고 라벨링한다.
이 규모는 **파일럿 평가셋**이다 — §5.4의 해석 규칙을 반드시 함께 적용한다.

## 5. 지표 `metrics-v1`

구현은 `evaluation/` 패키지에 있고 회귀 테스트는 `tests/test_metrics.py` 다.

### 5.1 답변 가능한 질문 (single · followup · filter)

`k ∈ {1, 3, 5, 10}`. 순위 지표는 **기준별로 각각** 계산한다.

| 지표 | 정의 | 기준별 | chunker 의존 |
|---|---|---|---|
| `EvidenceCoverage@k` | `\|(⋃ 상위 k chunk 구간) ∩ (⋃ evidence 구간)\| / \|⋃ evidence 구간\|` | **단일 값** | 아니오 |
| `Hit@k` | 상위 k에 qrel 적중이 하나라도 있으면 1 | any / strict | 예 |
| `Precision@k` | 적중 chunk 수 / **`k`** | any / strict | 예 |
| `MRR` | 첫 적중의 역순위 (없으면 0) | any / strict | 예 |
| `nDCG@k` | `DCG@k / IDCG@k`, `DCG = Σ (2^grade − 1)/log₂(rank+1)` | any / strict | 예 |
| `returned_count@k` | `min(k, len(검색 결과))` | 단일 값 | — |

- **`Recall@k` 와 `ChunkRecall@k` 는 만들지 않는다.** 분모가 청킹에 따라 변해
  `chunker_version` 을 넘는 비교가 성립하지 않는다. 커버리지는 `EvidenceCoverage@k` 로 잰다
- `Precision@k` 분모는 **`k` 로 고정**한다. 반환이 부족한 경우도 결과에 반영되고,
  그 사실은 `returned_count@k` 로 따로 보고한다. 의도적 기권은 §5.2로 분리한다
- `IDCG@k` 는 해당 기준의 **qrel 전체 grade 를 내림차순 정렬해** 상위 k개로 계산한다
- 여러 evidence span 은 **합집합 길이**로 계산한다
- 결과표에 **평균 chunk 길이**와 **평균 검색 컨텍스트 길이**를 함께 적는다

### 5.1.1 입력 검증 (통과하지 못하면 계산하지 않는다)

`chunk_id` 중복 · 검색 결과 내 `chunk_id` 중복 · `Ranking.qid ≠ Question.qid` ·
`char_start < 0` · `relevance_grade ∉ {1,2}` · `k` 가 양의 정수가 아니거나 중복 ·
순위에 없는 `chunk_id` · 답변불가 문항의 순위 평가 투입 — 전부 `EvalDataError` 로 중단한다.

검색 결과에 같은 chunk 가 두 번 들어오면 DCG 에 같은 근거가 두 번 더해져 nDCG 가
부풀려지므로, **`Ranking` 생성 단계에서 거부**한다.

### 5.2 답변불가 질문 — 평균에 섞지 않는다

정답이 빈 집합이라 Recall이 정의되지 않는다. 별도로 본다.

**이번 파일럿에서 보고하는 것은 검색기별 threshold sweep뿐이다.**

- `false_evidence_rate@θ` — 근거가 없는 질문인데 θ 이상의 근거를 반환한 비율
- `miss_rate@θ` — 근거가 있는 질문인데 θ 때문에 아무것도 반환하지 못한 비율

두 값을 **θ를 훑은 곡선으로** 남긴다. 하나의 표에 두 지표를 함께 그려야 맞교환이 보인다.

**하지 않는 것**

- 같은 평가셋에서 가장 좋은 θ 하나를 고른 뒤, 그 θ의 성능을 결과로 보고하지 않는다.
  같은 데이터에서 고르고 같은 데이터에서 평가하면 낙관적으로 치우친다.
- 운영에 쓸 θ가 필요해지면 **calibration set에서 정하고 test set에서 평가한다.**
  파일럿 규모에서 그렇게 나누면 양쪽 다 너무 작아지므로, 이번에는 나누지 않고 곡선만 보고한다.
- **순위만으로는 기권을 결정할 수 없다.** 순위는 항상 1위를 만들어 내기 때문에,
  "근거가 없다"는 판단에는 점수나 별도의 판정 기준이 필요하다. 이 사실을 결과에 적는다.

θ는 **검색기마다 따로 잡는다.** 점수 스케일이 다르기 때문이다 —
R0·R1은 TF·IDF 규모이고 RRF 점수는 `1/(k+rank)` 규모라 자릿수가 다르다.
하나의 θ로 여러 검색기를 비교하면 임계값이 아니라 스케일을 비교하게 된다.

서비스 API에는 이번에 임계값을 넣지 않는다. 평가 스크립트가 검색기를 직접 호출해
충분히 큰 k의 점수 목록을 받은 뒤, 그 위에서 θ를 훑는다.
`/retrieve` · `/ask` 의 응답 계약과 기존 테스트는 건드리지 않는다.

### 5.3 보고 규칙

- **평균만 보고하지 않는다.** 문항별 결과를 `metrics.json`에 전부 남긴다.
- **실패한 질문을 공개한다.** 어떤 유형에서 왜 틀렸는지 함께 적는다.
- 검색기가 기준선을 이기지 못해도 그대로 싣는다. **Dense나 Hybrid가 더 낮게 나와도 공개한다.**
- 결과표마다 다음을 함께 적는다 —
  `experiment_id` · 토큰화 방식 · 겹침 기준 · 평균 chunk 길이 · 평균 검색 컨텍스트 길이 ·
  `evalset_version` · 평가셋 커밋 해시 · 측정 커밋 해시
- **제외된 문항 수와 분모(n)를 표시하지 않은 macro 평균은 출력하지 않는다.**
  구현에서 평균은 값 하나로 존재하지 않고 `Mean(value, n, excluded)` 로만 만들어지며,
  포맷터가 그 셋을 항상 함께 찍는다
- `strict_reachable_count / answerable_count` 와 `strict_reachability_rate` 를 함께 적는다.
  strict 수치는 부분집합 위의 조건부 값이므로 reachability 없이 읽을 수 없다

### 5.4 통계 해석 — 파일럿 규모의 한계

20~30문항은 **파일럿 평가셋**이다. 다음을 지킨다.

- 평균값 차이만으로 **일반적인 우위를 주장하지 않는다.** "이 평가셋에서는" 을 붙인다
- 검색기 쌍마다 **문항별 paired difference를 공개한다** — 어떤 질문에서 이기고 졌는지
- 가능하면 **paired bootstrap으로 불확실성 구간**을 함께 낸다
- 구간이 겹치면 우열을 주장하지 않는다. "차이를 확인하지 못했다"로 적는다
- 표본이 작다는 한계를 결과 문서 첫머리에 적는다

## 8. 중단·보류 기준

- 라벨링에서 정답 구간이 모호한 질문은 평가셋에서 **뺀다.** 억지로 라벨링하지 않는다.
- R1b 후보 중 §2.1 기준을 만족하는 것이 없으면 **R1b를 건너뛴다.**
  건너뛰면 "토큰화 축을 통제하지 못했다"를 결과에 명시하고, R1a와 R2의 비교에 각주를 단다.
- 로컬 Dense 모델이 CI 제약(키·네트워크 없음)을 깨면 opt-in으로 분리하고, 그 사실을 결과에 적는다.
- 어느 단계에서 멈추더라도 그 시점까지의 결과는 `evidence/`에 남기고 공개한다.
